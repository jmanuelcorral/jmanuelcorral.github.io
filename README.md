# jmanuelcorral.github.io

Personal site and bilingual (Spanish/English) software engineering notebook,
built with [Astro](https://astro.build) and deployed to GitHub Pages.

Production site: [josecorral.dev](https://josecorral.dev/).

Spanish (`/es/`) is the canonical language; English (`/en/`) entries are
translations and may lag behind. The root URL (`/`) redirects to `/es/`.

## Content

- 10 bilingual blog posts (5 Spanish + 5 English translations) under
  `src/content/blog/{es,en}/`.
- 5 legacy Jekyll post URLs are preserved as static redirect stubs
  (see `src/pages/[legacy].astro` and `src/data/legacyRedirects.ts`) that
  forward to their corresponding Spanish post.
- `robots.txt`, `sitemap.xml` (via `@astrojs/sitemap`), and per-locale
  `rss.xml` feeds (via `@astrojs/rss`).
- `/llms.txt` and `/llms-full.txt` — machine-readable summaries of the site
  content for LLM tooling, generated at build time from the content
  collection.
- A custom 404 page.
- Design/reference HTML assets (CV, resume, palette/logo pages) served from
  `public/`. **No CV PDFs are published** — see [Privacy and contact
  information](#privacy-and-contact-information).

## Prerequisites

- **Node.js `>=22.12.0`** — required by Astro 7 (see
  `node_modules/astro/package.json` → `engines.node`). The GitHub Pages
  deploy workflow (`.github/workflows/deploy.yml`) uses `withastro/action`,
  which defaults to **Node 24**, so Node 22.12+ or 24.x both work locally;
  when in doubt, match CI and use Node 24.
- **npm `>=9.6.5`** (ships with the Node versions above).
- **Git**, to clone the repository.

Check your versions with `node --version` and `npm --version` before
continuing.

## Getting started

```bash
git clone https://github.com/jmanuelcorral/jmanuelcorral.github.io.git
cd jmanuelcorral.github.io
npm ci
```

`npm ci` installs the exact versions pinned in `package-lock.json` — always
use it instead of `npm install` for a reproducible environment.

### Windows PowerShell

The commands above work unchanged in PowerShell (`git clone ...`, `cd ...`,
`npm ci`). No Bash-only syntax is required anywhere in this workflow; where
a step below needs a different PowerShell command, it is called out
explicitly.

## Local development

Run these from the repository root:

```bash
npm run dev        # start the local dev server
npm run check      # type-check the project (astro check)
npm run build      # build the static site to dist/
npm run preview    # preview the production build locally
```

- **`npm run dev`** starts Astro's dev server, by default at
  **http://localhost:4321/** (Astro picks the next free port, e.g. `4322`,
  if `4321` is already in use — watch the terminal output for the actual
  URL). Stop it with `Ctrl+C` in the terminal it's running in (same key in
  PowerShell and Bash).
- **`npm run check`** runs `astro check` (type-checking for `.astro`
  files and content frontmatter). It should report `0 errors` before you
  push.
- **`npm run build`** produces the static site in **`dist/`**. Treat
  `dist/` as fully generated output — never hand-edit files inside it;
  re-run `npm run build` instead. `dist/` is git-ignored.
- **`npm run preview`** serves the built `dist/` output, also at
  **http://localhost:4321/** by default, so you can sanity-check the
  production build before pushing. Stop it with `Ctrl+C`.

## Content organization (ES/EN pairing)

Blog posts live under `src/content/blog/es/` and `src/content/blog/en/`,
one Markdown file per post, defined by the collection schema in
`src/content.config.ts`. Minimum required frontmatter for every post:

```yaml
title: 'Post title'
description: 'One-sentence summary'
lang: 'es'                 # or 'en' — must match the folder
translationKey: 'shared-key' # same value on both the es and en version of a post
slug: 'localized-slug'     # may differ per locale
pubDate: '2019-03-15T13:31:56-05:00'
tags: ['blog', 'personal']
draft: false
legacyPath: '/Old-Jekyll-Url' # optional, es-only — see redirects below
```

- `translationKey` is how an `es` post and its `en` translation are paired;
  both files must share the same value even though filenames and `slug`
  can differ per locale.
- `legacyPath` is only valid on `es` entries (enforced by a schema
  `refine`) since the original Jekyll site had no English posts.
- A new post needs at minimum the `es` file; add the matching `en` file
  (same `translationKey`) once the translation exists — English is allowed
  to lag behind Spanish.

## Generated artifacts — do not hand-edit `dist`

The following are all produced automatically by `npm run build` from
source/content, and only ever exist inside the generated `dist/` folder:

- **`llms.txt` / `llms-full.txt`** — built from the blog content collection
  by `src/pages/llms.txt.ts` / `llms-full.txt.ts`.
- **`sitemap-index.xml` / `sitemap-*.xml`** — generated by the
  `@astrojs/sitemap` integration configured in `astro.config.mjs`.
- **`rss.xml`** (per locale, `/es/rss.xml` and `/en/rss.xml`) — generated
  via `@astrojs/rss` from `src/pages/{es,en}/rss.xml.ts`.
- **Legacy redirect stubs** (e.g. `/Hello-World/`) — generated from
  `src/data/legacyRedirects.ts` by `src/pages/[legacy].astro`.

To change any of the above, edit the source files listed, then re-run
`npm run build` — never edit generated files inside `dist/` directly, since
the entire folder is overwritten on every build.

## Design source vs. production assets

- **`newdesign/`** is design source/reference material (HTML mockups, the
  design manifest/handoff notes) — it is not served by the site and is not
  part of the Astro build. Visual fidelity to `newdesign/` is mandatory when
  implementing UI, but privacy/security rules take precedence over fidelity
  (see below) and may require redaction/removal in both the design-source and
  production copies.
- **`public/`** holds the actual static assets served in production
  (`robots.txt`, design/CV **HTML** pages such as `cv.html`,
  `resume-short.html`, `resume-extended.html`, etc.) — these are copied as-is
  into `dist/` on build. **No CV PDFs are published** in `public/`, `dist/`,
  or anywhere else.

## Privacy and contact information

- **CV PDFs are permanently disallowed** from `public/`, `newdesign/`,
  source, and any generated output, unless the site owner explicitly
  reverses this policy. Only CV/resume **HTML** pages are published.
- **The owner's email address and any `mailto:` link must never appear** in
  public HTML, page metadata, structured data (JSON-LD), design-source
  exports (`newdesign/`), or generated output (`dist/`, `llms.txt`/
  `llms-full.txt`, RSS, sitemap). Public contact is via the existing GitHub
  and LinkedIn links already used on the site — no other contact URL should
  be added.

## Deployment

The site is a static Astro build deployed to **GitHub Pages** via
[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml), using the
official `withastro/action` and `actions/deploy-pages` GitHub Actions. The
workflow builds on every push to `master` that touches Astro source,
config, content, or public files, and can also be run manually via
`workflow_dispatch`. There are no manual deploy steps beyond a normal push
to `master` — GitHub Pages **Settings → Pages → Source** is already set to
"GitHub Actions", so a qualifying push triggers build + deploy end to end.

## Troubleshooting

If `npm run dev`/`build` behaves unexpectedly after a dependency or config
change, try these targeted steps in order — avoid broad/destructive
deletions (e.g. do **not** wipe the whole `node_modules/` or repo state
unless one of these first proves insufficient):

1. **Re-sync content types** — Astro's generated types can go stale:
   ```bash
   npx astro sync
   ```
2. **Clear Astro's local cache only** (safe, regenerated automatically):
   ```bash
   # Bash
   rm -rf .astro
   # PowerShell
   Remove-Item -Recurse -Force .astro
   ```
3. **Reinstall exactly what's locked** if `node_modules/` looks stale or
   corrupted, without touching the lockfile:
   ```bash
   # Bash
   rm -rf node_modules && npm ci
   # PowerShell
   Remove-Item -Recurse -Force node_modules; npm ci
   ```
4. Re-run `npm run check` and `npm run build` to confirm the issue is
   resolved before continuing.
